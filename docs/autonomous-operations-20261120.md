# Production dependency map and acceptance contract

Evidence baseline: 20 November 2026 15:08 Israel. Current live cron/dashboard a602b54.

| Origin | Propagation | Structural correction |
|---|---|---|
| Pacing, unfinished provider pagination and outstanding tax research share generic `partial` flags | All windows look failed; no clear distinction between discovery and processing | Persist a separate window contract with actual pages, source receipts, pending deliveries and explicit five outcomes; retain raw historic receipts |
| Cached source acknowledgments discard the original processing proof | A successful recovery/replay appears unchecked or partial | Preserve a compact source-processing summary with the immutable acknowledgment, without mailbox bodies |
| A global historic free-source ambiguity repeatedly marks each new successful intake partial | Five-minute repeated work, incident churn, and false critical cron failures | Distinguish a completed intake with evidence holds from transport/parser recovery; use normal source refresh cadence for the former, bounded retries for the latter |
| Canonical metadata fetched before delivery; email validates an unrelated legacy export | Newly delivered records lack links; an unrelated stale card can cancel the whole digest | Deliver before reporting, refresh signed canonical IDs, and validate only the frozen change manifest |
| Digest selects recent inventory, independently of prior sending | Stale pending properties and technical diagnostics repeat | Canonical change journal; frozen selection independent of inventory delivery; acknowledge only after confirmed email acceptance |
| Destination canonical identity absent from source decision feed | A new provider alias can be mistaken for a new property and links cannot be verified | Add signed canonical ID, original discovery date, and actual watch trigger provenance; never derive or guess destination IDs |
| Weighted page counters ignore coverage age and business yield | Small partitions rotate, but stale unfinished main partition may wait unnecessarily | Preserve every cursor; overdue coverage gets priority, then weighted fairness, unfinished progress and measured reviewable yield |
| A failed optional stage can interrupt later unrelated stages | Source/enrichment failure can prevent delivery, quality checks and receipts | Persist stage-specific recoverable failure, continue unaffected work, always close failure receipts |
| Transient sync requests can retry forever | Operational work remains stuck without explicit escalation | After twelve consecutive wire failures, hold the operation as a dead letter; retain payload and error, resume only through existing authorized recovery controls |

## Existing components deliberately preserved

Shared eligibility rules, official geographic exclusions, atomic purpose-specific budget accounting, frozen delivery payloads, price observation receipts, durable enrichment jobs, owner decision authority, Gmail/Follow-Up, PENTEN UI, existing Render services and PostgreSQL. No new subscription, provider scan, email, notification type or service is needed for validation.

## Monthly model

36 listing pages, 8 AVMs, 4 targeted requests and 2 recovery requests remain separate. Weighted release favors 08:00 windows, with occasional evening pages. All 08:00 and 20:00 processing windows still run. Capacity is checked again atomically at dispatch. No approval renews after 14 December 2026 12:00 Israel.

At the latest observed sizes (683 main-query listings, 14 Bethel Park, 9 Pleasant Hills), a configured-query traversal costs approximately 4 pages at 500 records/page: 2 main + 1 + 1. Thirty-six pages allow approximately 9 such traversals, about one every 3.3 days over 30 days, before changes in inventory and failures. RealScout/free evidence runs between provider requests. These are provider query estimates, never a verified municipal/market denominator. Purpose caps cannot be silently transferred.

## Seven-day acceptance

The deployed watchdog persists exactly fourteen future scheduled windows starting with the first slot after activation. It records actual commits, matching receipt pairs, requests, pages, new identities versus historical recovery, destination acknowledgments, source intake, prices, AVMs and critical failures. No future run is counted as passed. Current rolling seven-day evidence remains intact. The campaign has no provider/email execution capability.

Gates A–D require tests, deployed commits, unchanged owner data, valid budgets/cursors and no critical delivery backlog. Gate E requires actual scheduled execution after deployment. Operational stability requires the fourteen-window campaign plus continuing data-integrity/budget evidence; absence of qualifying listings is not itself a failure.

External dependencies: actual account-wide usage outside RentalSourcing cannot be independently measured by its ledger; official tax access restrictions remain enforced; ambiguous RealScout identities remain held; API feed geography is not identical to official boundaries. Current Render documentation retrieval was attempted via Markdown and HTML, but the execution network could not reach either; actual service metadata and bundled stable deployment guidance were used.
