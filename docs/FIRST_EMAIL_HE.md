# המייל הראשון — 17 באוקטובר 2026, 08:00 בישראל

הפעולה משתמשת במסד הקיים בלבד. אין להפעיל RentCast, לשנות מכסות, לשדרג מנוי או להקים שירות חדש.

## בשירותים הקיימים ב־Render

1. לאחר מיזוג הקוד לפרוס את master ב־rentalsourcing-dashboard וב־rentalsourcing-daily דרך Manual Deploy → Deploy latest commit. עליית ה־Web מריצה מיגרציה ובדיקה חוזרת של הרשומות, ללא API. המיקודים 15210, 15203, 15204 נפסלים גם בהצגת הדשבורד ובשליחה עצמה. ההיסטוריה והמטמון נשמרים.
2. בשירות rentalsourcing-daily, Settings, לשנות Schedule ל־`0 5,6 * * *` ואת Start Command ל־`python -m rentalsourcing.cloud --scheduled-email`. זהו השירות הקיים, לא Blueprint חדש. הקוד מאפשר רק את חלון 08:00 Asia/Jerusalem. ב־17/10/2026 זה 05:00 UTC; בחורף 06:00 UTC. מפתח outbox ייחודי לתאריך הישראלי ונעילת PostgreSQL מונעים שליחה כפולה. שירות הדואר אינו יוצר Client של RentCast, גם אם משתנה ישן איפשר איסוף.
3. ב־Environment של rentalsourcing-daily להגדיר בפרטיות RESEND_API_KEY, EMAIL_FROM משולח מאומת ב־Resend ו־EMAIL_TO. להשאיר ENABLE_EMAIL=false ו־ENABLE_RENTCAST=false. אין לשנות את מכסות ה־API.

## הכנה ללא שליחה

ב־Shell של שירות קיים שמחזיק את אותם DATABASE_URL ומשתני מייל:

```sh
python -m rentalsourcing.cloud --prepare-email --email-day 2026-10-17
python -m rentalsourcing.cloud --prepare-test-email
```

הפקודות שומרות טיוטות ב־outbox ומדפיסות מזהים בלבד; הן אינן שולחות. מייל הניסיון אינו כולל הזדמנויות ואינו מסמן נכסים כנשלחים, כך שלא יצרוך את הזדמנות המייל הראשון למחרת. טיוטת המייל הראשון כוללת רק רשומות אמיתיות שעוברות את כל הבדיקות עם מס שמור תקף ומודעה שנצפתה ב־24 השעות האחרונות. אם אין כאלה, מתקבל עדכון אמיתי על הנתונים השמורים. אין טענה שבוצעה סריקה חדשה.

בפרט, 1020 Sutherland St במיקוד 15204 אינו יכול להיכלל. 1034 Elwell St ייכלל רק אם נתוני הייצור השמורים עוברים את הבדיקות; אין בסביבה המקומית הוכחה לכך. לא מאריכים תוקף של ראיות ישנות כדי לכלול נכס.

## רק לאחר אישור מפורש לשולח, לנמען ולשליחת ניסיון

להגדיר EMAIL_APPROVAL_ID למזהה האישור ו־ENABLE_EMAIL=true בשירות. אין לעשות זאת לפני האישור. להכין מחדש את מייל הניסיון כדי לקשור אותו למזהה האישור, ואז להשתמש במזהה test- שהודפס:

```sh
python -m rentalsourcing.cloud --prepare-test-email
python -m rentalsourcing.cloud --retry-email TEST_OUTBOX_ID
python -m rentalsourcing.cloud --email-status TEST_OUTBOX_ID
```

יש להחליף TEST_OUTBOX_ID במזהה המלא שהתקבל. `sent` משמעו קבלת בקשה אצל Resend; רק `delivered=true` מבדיקת המצב מאמת מסירה אצל הספק. לחלופין אפשר לבדוק ב־Resend → Emails את אירוע Delivered של אותו מזהה. אין לשלוח שוב עם מזהה חדש כשמצב השליחה לא ודאי. לאחר 23 שעות נדרש בירור ידני במקום ניסיון אוטומטי.

לאחר הניסיון המאושר ובדיקת המסירה, להכין שוב את הטיוטה לתאריך 2026-10-17. ה־Cron יבצע בדיקה חוזרת סמוך לשליחה. מייל שהשתנו בו קריטריונים לפני הניסיון הראשון מוחלף בבטחה; לאחר ניסיון שמצבו לא ודאי הוא מוקפא לבירור, ולא נשלח מחדש עם נכס מוחרג.

נדרשת גישת Render ופרטי Resend כדי לאמת שההגדרות פעילות, שהטיוטה מכילה נתוני ייצור ושהמייל נמסר. ללא גישה זו אי אפשר להבטיח את מועד המסירה.
