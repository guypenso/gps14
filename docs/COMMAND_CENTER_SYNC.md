# Inspection Command Center: Phase 1

This change is disabled by default. It does not alter discovery, criteria,
RentCast allowances, daily timing, email envelopes, or Resend idempotency keys.

## Data path

1. Existing `Digest.prepare` / `prepare_stored` freezes an allowlisted structured
   snapshot of **the same selected cards**, alongside the existing email outbox.
   No email parsing and no raw listing export. Preview/test emails are excluded.
2. Only daily outbox rows marked `sent` (Resend **accepted**, not proof of inbox
   delivery) can synchronize. Pending, cancelled, failed and uncertain emails do
   not publish. Old emails without snapshots are not reconstructed.
3. After email acceptance, the existing send wrapper attempts up to three pending
   snapshots. HTTPS only, five-second timeout per report, no redirects/immediate
   retries. Failures retain their exact payload, attempt count and error category
   for a later existing daily execution. Email acceptance is never rolled back.
4. Command Center validates HMAC-SHA256 over `timestamp + '.' + raw_body`, a
   five-minute timestamp window, a permanent report ID/content hash, and its
   existing Sites service-access boundary. Neither secret reaches the browser.
5. D1 stores identities, reports and review decisions separately from inspection
   workspaces. Rejected properties retain only a permanent tombstone and hashed
   address/provider aliases. Re-imports and price changes cannot restore them.

Report contract: `schema_version=1`, stable daily `report_id`, `report_date`,
`prepared_at`, `discovery_state`, `opportunities[]`. The shared fictional fixture
in `tests/fixtures/command-center-report.json` is generated by the actual daily
pipeline using mocked providers. It is also tested by the Command Center Worker.
Per-property fields include provider identity, address/unit/ZIP, price and prior
price, beds/baths/area, annual tax/year/provenance, qualification, report section,
missing-data reasons, original listing URL and evidence/discovery timestamps.
Unknowns remain null. `provider_verified` tax is not an official-bill assertion.

## Configuration (after explicit production approval)

On the **existing cron only**, add private server-side values:

| Variable | Value |
| --- | --- |
| `ENABLE_COMMAND_CENTER_SYNC` | `false` during deployment; `true` only on activation |
| `COMMAND_CENTER_SYNC_URL` | `https://<existing-command-center-site>/api/rentalsourcing/sync` |
| `COMMAND_CENTER_SYNC_SECRET` | A new random 32+ character secret; same private value on the receiver |
| `COMMAND_CENTER_SERVICE_TOKEN` | Existing supported Sites service-access credential for this exact Site |

On Command Center, `ENABLE_RENTALSOURCING_SYNC=false` initially and
`RENTALSOURCING_SYNC_SECRET` matching the sender. Do not put credentials in chat,
Git, the hosting manifest, frontend JavaScript, or linked environment groups.
Sites service access is sent as `OAI-Sites-Authorization: Bearer ...`; this is
separate from the HMAC secret. The Site remains restricted to its current audience.
Its existing authorized collaborators share this inbox and review decisions,
just as they share inspection workspaces; no audience change is included.

## Approved-release sequence

1. Preserve current release SHAs, PostgreSQL backup and the current Sites version. Keep
   Render Auto-Deploy off. Back up the existing D1 database before migration.
2. Publish the reviewed Command Center saved version with receiving disabled.
   Sites applies additive `0002_rentalsourcing.sql`; existing tables/files stay.
3. Merge the reviewed RentalSourcing PR only after approval. Manually deploy the
   same resulting SHA to the existing dashboard then cron, outside an active run.
   Existing startup migration adds `command_center_reports` and schema version 3.
   It does not reset usage/outbox or delete/rewrite history. No command or schedule
   changes are part of this integration. Keep the new sender flag off initially.
4. Configure the private credentials on the two backends. Enable receiving first,
   then sending on the cron. Leave all email/discovery approvals and budgets as-is.
5. Observe the next normal daily email and corresponding report in Command Center;
   compare selected identities, pending status, prices, and links. Do not trigger
   another scan/email or bypass a sent daily outbox key. A controlled mock-only
   staging acceptance test can precede this without touching provider accounts.

Rollback: disable only the new sender/receiver flags, then restore the prior code
versions if needed. Keep both additive schemas, snapshots and rejection aliases;
do not delete tombstones, reset counters, or rewrite frozen emails. A later
reenablement safely resumes snapshots not yet acknowledged by the receiver.

## Verified boundaries

Source and receiver code access, existing Site identity/bindings and live D1 table
names were inspected. Production Render settings/PostgreSQL were not accessible
in this environment. Tests use SQLite and isolated PostgreSQL, never production.
No new subscription, service, RentCast request, email or deployment is performed.
Browser layout QA remains unverified; real click handlers are exercised using a
DOM adapter against the real Worker and a SQLite-backed D1 test database.
